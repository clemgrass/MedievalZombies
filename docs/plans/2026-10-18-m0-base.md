# M0 – Base del proyecto: plan de implementación

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Objetivo:** dejar listo el sistema de trabajo: `docs/` con plantilla de ADR,
convenciones, sistema de tickets en GitHub (plantillas, labels, milestones, Project),
ADRs 0001 y 0002 aceptados, y el autor sabiendo usar todo esto por su cuenta.

**Arquitectura:** todo es documentación en Markdown dentro del repo, configuración de
GitHub (issue forms en YAML, labels, milestones y Project vía `gh`) y una sesión
guiada. No hay código del juego.

**Stack:** Markdown, GitHub Issue Forms (YAML), `gh` 2.100, `jq`, `python3` + PyYAML
(solo para validar YAML).

**Spec:** `docs/specs/2026-10-18-base-del-proyecto-design.md`

## Restricciones globales

- Todo en español. Los tipos de Conventional Commits (`docs:`, `feat:`…) quedan en inglés.
- Todo gratis.
- Repo: `clemgrass/MedievalZombies` (público), rama por defecto `main`.
- Labels exactos: `tipo:épica`, `tipo:feature`, `tipo:tarea`, `tipo:bug`,
  `tipo:investigación`, `área:graphics`, `área:slicing`, `área:physics`,
  `área:animation`, `área:ai`, `área:gameplay`, `área:tooling`, `área:docs`,
  `modo:dirigido`, `modo:propuesto`.
- Campos del Project: Estado = `Backlog`, `Listo`, `En progreso`, `En revisión`,
  `Hecho`. Prioridad = `Alta`, `Media`, `Baja`. Tamaño = `S`, `M`, `L`.
- ADRs: numeración global `ADR-NNNN`, archivo `NNNN-titulo-corto.md`, estados
  `Propuesto`, `Aceptado`, `Reemplazado`, `Descartado`.
- Las secciones "Decisión" y "Cómo lo defiendo" de cada ADR salen del **autor**:
  Claude solo mejora la redacción, sin cambiar las ideas.
- Los planes viven en `docs/plans/`, junto a `docs/specs/`.

## Puntos a revisar

1. **Labels con tildes y dos puntos.** `tipo:investigación` tiene que coincidir
   *byte a byte* entre `setup-labels.sh` y el campo `labels:` de los issue forms. Si
   no coinciden, GitHub ignora el label en silencio. Lo verifica el Task 3, paso 4.
2. **Filtrar por esos labels.** `gh issue list --label "tipo:investigación"` tiene que
   devolver resultados. Lo verifica el Task 3, paso 6.
3. **Workflow "Item closed → Hecho".** Al renombrar las opciones de Estado, el
   workflow nativo tiene que quedar apuntando a `Hecho`, o los issues cerrados no se
   mueven. Lo verifica la sesión guiada (Task 6, paso 6).
4. **Índice de ADRs desactualizado.** Un ADR nuevo que no aparece en `docs/README.md`
   rompe el criterio de éxito "índice completo". Lo verifica el Task 5, paso 5.
5. **Issue forms fuera de `main`.** GitHub solo muestra plantillas que están en la
   rama por defecto, así que se hace push antes de probarlas. Lo verifica el Task 3,
   paso 5.

### Task 2: Convenciones git y guía de tickets · owner: claude

**Archivos a crear:** `docs/process/git.md`, `docs/process/tickets.md`

**Interfaces:**
- Consume: los labels y campos de las Restricciones globales.
- Produce: la convención de ramas `<N>-<descripcion-corta>` (N = número de issue) y el
  flujo de PR con squash merge que usa el Task 6.

- [ ] **Paso 1: escribir `docs/process/git.md`.**
  - **Commits:** Conventional Commits (`feat`, `fix`, `docs`, `refactor`, `test`,
    `build`, `chore`), con descripción en español.
  - **Ramas:** una por ticket, con nombre `<N>-<descripcion-corta>`.
  - **Integración:** PR a `main` con squash merge. El cuerpo del PR lleva
    `Closes #N`, así cada ticket queda como un commit en `main`.
  - **Excepción:** commits directos a `main` solo para cambios triviales de docs, con
    `Refs #N` si aplica.
- [ ] **Paso 2: escribir `docs/process/tickets.md`.** Es una guía para alguien que nunca
  usó GitHub Projects:
  - la tabla de conceptos (issue, sub-issue, label, milestone, project, `Closes #N`) con
    su equivalente en Jira;
  - jerarquía, labels, campos, y Definición de Listo y de Hecho (copiados de 2.2 a 2.6
    de la spec);
  - "Cómo hago X", con la ruta en la web y el comando `gh` equivalente para: crear
    issue, agregar sub-issue, poner label o milestone, mover de estado y cerrar desde
    un PR.
  - Nota: el `modo` se elige en el formulario del issue, pero el label `modo:` se
    pone al refinar. Sin él, el ticket no pasa a `Listo`.
- [ ] **Paso 3: verificar.** Ejecutar `grep -oE '(tipo|área|modo):[a-záéíóú]+' docs/process/tickets.md | sort -u | wc -l`.
  Esperado: `15`.
- [ ] **Paso 4: commit.** `docs: convenciones git y guía de tickets`
